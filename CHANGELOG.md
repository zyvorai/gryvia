# Changelog

All notable changes to Gryvia are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the project aims to follow [Semantic Versioning](https://semver.org/) once it leaves alpha.

## [Unreleased]

Entries are newest first within each section. Counts in an entry (for example "24 programs") are as of that entry; the
current numbers are 47 CRDs (43 with a registered controller) and 47 eBPF programs.

### Added
- Job hooks deliver from a worker pool ([docs/job-hooks.md](docs/job-hooks.md#delivery)): the job reconcilers only queue due deliveries; `--job-hook-workers` (`aiOperator.jobHooks.workers`, default 8) goroutines POST them, record the outcome on the job with a conflict-retried update, and enqueue the job again. A slow receiver no longer holds a reconcile for every hook of a job in turn; a full queue (256) retries the job after a second. Delivery stays at least once.
- Agents stream ([docs/agents.md](docs/agents.md#streaming)): the agent runtime accepts `"stream": true` (it returned 400 before). It streams each model call from the LLM gateway, relays the text as `chat.completion.chunk` server-sent events, assembles tool calls from their deltas, sends one extra event per tool call it runs, and ends with an event carrying the summed `usage` and the `gryvia` block, then `[DONE]`. A gateway error before the first event keeps its HTTP status; after it, the error is an event. `POST /api/agents/{name}/chat` takes `"stream": true` and relays the events. The kind e2e streams a tool-using chat through the api-gateway.
- LLM gateway: `tokensPerDay` is shared across replicas ([docs/llm-gateway.md](docs/llm-gateway.md#quotas)). Today's counts live in a ConfigMap per UTC day (`gryvia-llm-tokens-<date>`, release namespace); every `--quota-sync-interval` (`llmGateway.quotaSyncInterval`, default 1s) each replica adds its counts with an optimistic-concurrency update and reads back the totals. A replica sees the others' traffic within about two intervals, instead of only as of a once-a-day read of the usage records. The first replica of the day seeds the counter from that day's records; counters older than yesterday are deleted. The chart adds `POD_NAMESPACE` and a Role for ConfigMaps in the release namespace. The kind e2e runs two gateway replicas and expects a 429 from each.
- Job hooks (opt-in: `aiOperator.jobHooks.enabled`, `--enable-job-hooks`; see [docs/job-hooks.md](docs/job-hooks.md)): `GryviaJobHook` is rebuilt as a namespaced kind (`gjh`) with a controller. When a `GryviaAIJob` or `GryviaWorkflow` in the hook's namespace reaches one of its events (`Running`, `Succeeded`, `Failed`, `Cancelled`, `Preempted`, `Rejected`), filtered by kind and label selector, the ai-operator POSTs a JSON body (or a Slack `{"text"}` message), signed with HMAC-SHA256 like the budget webhook when `secretRef` is set, with `X-Gryvia-Event` and a stable `X-Gryvia-Delivery` id. Failed POSTs are retried with doubling backoff up to `retry.attempts`; delivery is at least once, recorded per job in the `gryvia.io/job-hooks` annotation; transitions older than the hook are not delivered. The dialer refuses loopback, private, CGNAT, link-local (including the metadata address), multicast and reserved addresses after DNS resolution unless they are in `aiOperator.jobHooks.allowedCIDRs`, and plain http only goes to those CIDRs. Status reports a Ready condition, delivery and failure counts and the last delivery. Gateway routes `/api/job-hooks` (create, list, get, suspend, delete; header values are never returned) and `gryvia job-hooks`. The old cluster-scoped schema (exec, k8s-job, notification actions) never ran and is not carried over.
- Agents (opt-in: `aiOperator.agents.enabled`, `--enable-agents`, needs `llmGateway.enabled`; see [docs/agents.md](docs/agents.md)): new `GryviaAgent` kind (namespaced, `gag`): a model on the LLM gateway, a system prompt and tools (`retrieval` over a `GryviaVectorIndex` through `/v1/retrieve`, or `http` with a URL-prefix allowlist and GET/POST), served as an OpenAI-compatible `/v1/chat/completions`. The ai-operator runs a runtime Deployment (non-root, read-only root filesystem, no service account token), a Service and a config ConfigMap per agent, issues it its own gateway key and writes a NetworkPolicy: ingress from the agent's namespace and the api-gateway, egress only to DNS, the gateway pods and the tool hosts (public hostnames on their port outside private ranges). The reference runtime (`examples/agents`, image `ghcr.io/zyvorai/gryvia-agent-runtime`, FastAPI) runs the tool-calling loop for at most `maxSteps` model calls (the last without tools), checks URLs by scheme, host, port and normalized path, and returns summed usage and a `gryvia.toolCalls` trace. New api-gateway routes `/api/agents` (CRUD, `scale`, and `chat`, proxied to the runtime), `gryvia agents list|get|create|delete|chat`, and an Agents dashboard page with a chat panel. Also fixes `DeleteOwnedKey` removing the store credential of a vector index with the same name as another owner. Unit-tested and run on kind with a stand-in tool-calling model; not tried with a real vLLM tool-calling model.
- RAG (opt-in: `aiOperator.rag.enabled`, `--enable-rag`, needs `llmGateway.enabled`; see [docs/rag.md](docs/rag.md)): new `GryviaVectorIndex` kind (namespaced, `gvi`). For each index the ai-operator keeps a managed Qdrant (non-root `-unprivileged` image, StatefulSet with a volume) or uses an external Qdrant (its API key mirrored for the gateway), issues the index its own LLM gateway key, and runs an ingestion Job per dataset version, spec change, `gryvia.io/reingest` value or `schedule` tick. The reference image `examples/rag` (`ghcr.io/zyvorai/gryvia-rag-ingest`, standard library only, built by `images.yml` and `release.yml`) chunks text, JSONL and HTML files, embeds them through the gateway and switches a collection alias. The LLM gateway serves `POST /v1/retrieve` (`index`, `query`, `topK`): scoped to the key's namespace, the query embedding metered and subject to `tokensPerDay`. Gateway routes `/api/vector-indexes` (create, reingest, suspend, resume, delete), CLI `gryvia rag index|reingest|query`, dashboard page "Vector indexes", tenant roles. Unit-tested (controller, `/v1/retrieve`, `ingest.py`, routes, CLI, UI helpers); covered by RAG steps in `e2e-ml.yml` with the real Qdrant and ingestion images and a stand-in embeddings server. Not run with a real embedding model.
- LLM gateway (opt-in: `llmGateway.enabled`; see [docs/llm-gateway.md](docs/llm-gateway.md)): `/manager llm-gateway`, a new mode of the ai-operator image, serves `/v1/models`, `/v1/chat/completions`, `/v1/completions` and `/v1/embeddings` in front of every `GryviaInferenceService` annotated `gryvia.io/llm-model` (optional `llm-served-model`, `llm-shared` and per-model prices). Per-tenant keys are stored only as sha256 in Secrets of a dedicated namespace (`llmGateway.keyNamespace`); a key reaches its namespace's models and the shared ones. Streaming is relayed event by event with `stream_options.include_usage`; tokens are exported as `gryvia_llm_tokens_total{tenant,model,type}` and written every 5 minutes as hourly `GryviaUsageRecord`s with the new `kind: tokens`, `model`, `inputTokens` and `outputTokens` fields. New `GryviaQuota.spec.tokensPerDay` is enforced with HTTP 429 (approximate with several replicas). Gateway routes `/api/llm-keys`, `/api/llm/models` and `/api/llm/usage`, CLI `gryvia llm keys|models|usage`, dashboard page "LLM gateway", `examples/llm-gateway`. Unit-tested with `httptest` upstreams and fake clients; covered by an LLM gateway step in `e2e-ml.yml` with a stand-in OpenAI server. Not run in front of vLLM.
- Model factory quantization: `examples/model-factory/quantize.py` writes AWQ (default `W4A16_ASYM`) or GPTQ 4-bit weights with llm-compressor, calibrated on the training JSONL, in the compressed-tensors format, and reports `path`, `subPath`, `format`, `quantization`, `method` and `scheme`. `model-watch.yaml` gains a quantize step between fine-tune and evaluate (the evaluation scores the quantized model) and passes `--quantization` to vLLM; the image installs llm-compressor. No CRD change. Argument parsing and calibration data are unit-tested; the e2e model factory template has a quantize stand-in. Not run on a GPU.
- Continuous evaluation and auto-rollback ([docs/model-evaluation.md](docs/model-evaluation.md)): `GryviaModelRegistry.spec.rollbackPolicy` (`metric`, `threshold`, `direction`) rolls a shared service back to `status.previousVersion` when the served entry's metric crosses the threshold, or on request (annotation `gryvia.io/rollback-requested`, set by the new `POST /api/models/{name}/rollback` and `gryvia models rollback`). The previous entry returns to production, the service's `modelRef` and stable pods go back to it, the entry is archived with condition and Event `RolledBack`; refusals are reported as `RolledBack=False` and `RollbackRefused`. New workflow step type `registry` (`entry` or `serviceName`, `action: updateMetadata|rollback`, templated `metadata`); register steps can set `rollbackPolicy`. `evaluate.py --endpoint` scores a live OpenAI-compatible server; `examples/model-factory/eval-schedule.yaml` re-scores the served version nightly. Unit-tested through both controllers; covered by a step in `e2e-ml.yml`. Not run against a real model.
- Datasets (opt-in: `storageOperator.datasets.enabled`, `--enable-datasets`; see [docs/datasets.md](docs/datasets.md)): `GryviaDataset` gets a controller in the storage-operator and is no longer deprecated. It downloads an http (optional sha256 checksum file), s3 or nfs source into an owned PVC, one directory per version, with a non-root download Job; keeps the last `versioning.retentionPolicy.keepLast` versions; reports state, PVC, subPath, file count, bytes and content hash. New `spec.namespace` (where the PVC lives). Gateway routes `/api/datasets`, CLI `gryvia datasets`, dashboard page "Datasets", `examples/datasets`. Unit-tested; the http path is covered by a Datasets step in `e2e-ml.yml` (stand-in file server). s3 and nfs have not run against a real bucket or export.
- Model factory (opt-in: `aiOperator.modelWatch.enabled`, `--enable-model-watch`; see [docs/model-factory.md](docs/model-factory.md)): new `GryviaModelWatch` kind polls the Hugging Face Hub, filters new models by author, name, pipeline tag, downloads, license and size, estimates GPUs and starts one `GryviaWorkflow` per model from a template. `GryviaWorkflow` gains step outputs (termination message or `gryvia.io/output-<key>`), `{{steps.*}}`/`{{parameters.*}}`/`{{workflow.*}}` templating, a `register` step type and an optional cron `schedule`. `GryviaModelRegistry` gains `promotionPolicy` (promote a staging entry whose metric beats production) and `servingConfig.serviceName` (all versions share one inference service; a promoted version is canaried and promoted or rolled back, the replaced one archived). The stable and canary Deployments now load their own version's artifacts. Gateway routes `/api/model-watches`, CLI `gryvia models watch`, dashboard page "Model factory", and `examples/model-factory` (download, TRL/PEFT LoRA fine-tune, lm-eval evaluation scripts and image). Unit-tested; the model factory steps of `e2e-ml.yml` (stand-in hub, busybox steps) passed on a single-node k3s cluster without GPUs and in kind CI. No real download, fine-tune, evaluation or vLLM serving of a fine-tuned model has run.
- Placement benchmark: `scripts/placement-benchmark.sh` runs four Janus-format fixtures (`tests/placement/`, copied from Janus, Apache-2.0) through the real node-selection code and fails when makespan, mean wait or utilisation worsens by more than 1% against `baseline.json`; new CI workflow `placement-benchmark.yml`. Placement quality only, not NCCL/RDMA/training performance.
- API gateway audit trail: every state-changing request (including failed logins and 401/403 refusals) is recorded with time, request id, auth method/role/tenant/OIDC subject, method, route, status, outcome, peer address and duration. Never the Authorization header, query string or body. Sinks: the `gryvia.audit` JSON log (durable), optional `GRYVIA_AUDIT_FILE` (0600 JSON lines) and a bounded per-replica buffer behind admin-only `GET /api/audit`; metric `gryvia_gateway_audit_events_total`. Replaces relying on the deprecated `GryviaAudit` CRD. The shared API key is still one identity.
- Opt-in `pack` node scoring: a `GryviaAIJob` annotated `gryvia.io/placement-strategy: pack` prefers the node with the fewest free GPUs that still fit, keeping whole nodes free for large jobs. The default is unchanged (spread). Found and checked with `placement-sim`; not measured on a cluster.
- `placement-sim` (`operators/ai-operator/cmd/placement-sim`, [docs](docs/placement-sim.md)): replays a Janus cluster and workload through the real node-selection code with a fake client, so placement can be evaluated without GPUs. Placement only; not NCCL, RDMA or training performance.
- GPU sharing: opt-in `gpuOperator.devicePluginConfig` (flags `--device-plugin-config-name/-namespace`): a time-slicing `GryviaGPUSharingPolicy` writes the device-plugin ConfigMap key for its own `maxPodsPerGPU` and labels nodes with it, instead of relying on the chart's fixed replica count. Fake-client tested; not run against a real device plugin.
- Opt-in placement pinning: a `GryviaAIJob` annotated `gryvia.io/pin-placement: "true"` gets required node affinity on the nodes the operator chose, so the placement hold is binding. Unit-tested; not run on a cluster.
- Placement holds (opt-in: `--placement-holds`, chart `aiOperator.placementHolds`, off by default): while a job's pods come up, the GPUs of the nodes the operator placed it on count as used for other jobs' placement, until all its replicas are ready, it ends or is deleted, or five minutes pass. Before, GPUs counted as used only once a pod was bound to a node, so two jobs placed within seconds of each other were told the same GPUs were free. A single distributed job was already placed all-or-nothing (too few nodes keeps it `Pending`). The hold is in memory and advisory: pods carry a label node selector, not the chosen node names, so with spare matching nodes they can land elsewhere; fabric-aware ranking is unchanged. Unit-tested with fake clients; not run on GPUs. It is not the in-tree gang scheduler, which is still not called.
- Opt-in eBPF programs (`-enable-programs`, chart `ebpf.enablePrograms`): `nccl_transport`, `p2p_fallback`, `capture_gate`, `gpu_oom`, `graph_stall`, `gdr_fail`, `infer_ttft`, `weight_mmap`, `gpu_dev` and `ucx_complete`, whose signals or counters nothing in the collector reads yet, are no longer loaded by default (the collector's loader used to attach every object it found, so `capture_gate` cost a map lookup per TCP send for nothing). The value is a list of names or `all`; an unknown name stops the collector at start. Skipped programs are listed in `/api/v1/ebpf/status` with `notRequested: true` and get no `gryvia_ebpf_program_attached` series.
- eBPF XDP chaining (opt-in: collector flag `-xdp-mux`, chart `ebpf.xdpMux`, needs `-iface`): `xdp_mux` is the interface's only XDP program and tail-calls the first populated slot of `xdp_features`; `roce_cnp`, `pfc_pause`, `dns_tracker`, `packet_filter` and the new `roce_ecn` each tail-call the next populated slot (`ebpf/headers/xdp_chain.h`), so every loaded feature sees every packet instead of one XDP program per interface. The collector's `Manager` attaches the mux and places the features in their slot with a shared prog array (`collector/pkg/loader/xdpmux.go`). Tested in CI with `BPF_PROG_TEST_RUN` and through the collector on the loopback interface; not run on a NIC, and the per-packet cost is unmeasured. A feature attached on its own behaves as before.
- Twelve more observe-only eBPF programs (47 in total): `xdp_mux`, `roce_ecn`, `nccl_transport`, `p2p_fallback`, `capture_gate`, `gpu_oom`, `graph_stall`, `gdr_fail`, `infer_ttft`, `weight_mmap`, `gpu_dev` and `ucx_complete`, with fabric signal types 11 to 22 (14 and 23 are reserved). They build for x86_64 and arm64 and load through the kernel verifier in CI; they have not run on hardware. Nothing in the collector interprets the new signal types yet (the fabric folder ignores them) and the maps that steer `nccl_transport`, `capture_gate` and `gpu_dev` are never written, so ten of them are opt-in (see below). `fabric.TransportHint` classifies `NCCL_*` environment variables but is not called yet.
- Inference canary SLO gating (opt-in): with `aiOperator.inferencePrometheusURL` (flag `--inference-prometheus-url`) the operator reads the canary's 60-second error ratio, p95 latency and request volume from Prometheus with fixed queries, counts measured breaches through the existing health-check rollback policy and blocks promotion on missing, stale or insufficient telemetry (condition `CanaryAnalysisReady`). Default services are unchanged. Not run against a live Prometheus or real traffic; see [docs/inference-serving.md](docs/inference-serving.md).
- Inference GPU/RPS autoscaling and weighted canaries: `targetGPUUtilization` and `targetRequestsPerSecond` now produce HPA Pods metrics (CPU 80% stays the fallback, with a 300 s scale-down window) and an `AutoscalingReady` condition; opt-in Gateway API routing (`aiOperator.inferenceGatewayRouting`) reconciles an owned `HTTPRoute` with stable and canary weights and gates promotion on `Accepted`/`ResolvedRefs`. Needs a custom-metrics adapter and a Gateway controller; tested against a real API server (envtest), not against a data plane, GPUs or live traffic.
- Strict Kueue admission and recovery hooks (opt-in): `aiOperator.kueueStrictAdmission` makes tenant batch jobs fail closed when their LocalQueue is missing and lets queued GPU jobs create their suspended Job without free GPU nodes; optional required worker anti-affinity across hostnames; a cooperative checkpoint `preStop` hook, persistent `/data` and a resume environment contract, with a runnable CPU example. Not run on real GPUs; the hooks do not guarantee a save before eviction. See [docs/admission-recovery.md](docs/admission-recovery.md).
- NVIDIA one-click extras (all opt-in): the NVIDIA Network Operator (`nvidiaNetwork`, with an optional `NicClusterPolicy`) and NIM Operator (`nvidiaNim`) sub-charts, a time-slicing ConfigMap and post-install `nvidia-smi` Job (`nvidiaPlatform`), and `GryviaGPUSharingPolicy` writes the node labels the GPU Operator reads (`nvidia.com/device-plugin.config`, `nvidia.com/mig.config`) once its controller is enabled with `gpuOperator.gpuSharing` (see Fixed: it was never registered before). RDMA, GDS and MIG flags are passed through to the GPU Operator. Chart pins resolve on NGC and image tags were checked; not run on real GPUs, NVSwitch or InfiniBand. See [NVIDIA one-click](website/docs/guides/NVIDIA_ONE_CLICK.md).
- GPU smoke job and evidence collector: `examples/validation/gpu-smoke.yaml` requests one `nvidia.com/gpu` and logs `nvidia-smi`; `scripts/record-gpu-validation.sh` writes the nodes, allocatable GPUs, `GryviaGpuNode` objects and the job log to one report. Not a benchmark; not run on a GPU. See [docs/gpu-validation.md](docs/gpu-validation.md).
- `GryviaUsageRecord` immutability: a validating webhook on `gryviausagerecords` (`quotaOperator.usageRecordWebhook.enabled`, default on, failure policy `Fail`, own certificate and Service) rejects any change to `spec` once `spec.final` is true, including clearing `final`; growth while open, labels, annotations, creates and deletes are allowed. Verified on a live k3s cluster. See [SECURITY.md](SECURITY.md).
- AIJob lifecycle: `training`, `fine-tuning` and `evaluation` `GryviaAIJob`s now run as an Indexed `batch/v1` Job (`inference` stays a StatefulSet; `spec.workloadKind` is the escape hatch, `spec.suspend`, `retryLimit` and `timeout` are honoured, `RANK`/`NODE_RANK` and a namespace-qualified `MASTER_ADDR` are set), so `Succeeded` and `Failed` are reachable and usage records finalize. `Queued`, `Rejected`, `Preempted` and `Cancelled` are honoured by the controller (`Rejected` is sticky), the quota operator patches only `phase`/`message`/`conditions`, and `gpus: 0` runs a CPU-only job. The chart gains RBAC on `batch/jobs`. Never migrated in place: an existing StatefulSet or Job of a job is kept. Unit-tested with fake clients; the kind workflow `.github/workflows/e2e-jobs.yml` is authored and had not been run when this was written; nothing has run on GPUs or RDMA hardware. See [docs/aijob-lifecycle.md](docs/aijob-lifecycle.md), which also lists the order of the gates in `reconcileAIJob`.
- Kueue integration (opt-in, default off; stacked on the AIJob lifecycle): with `aiOperator.kueueIntegration` a job with a queue (`spec.queueName`, annotation `gryvia.io/queue-name`, or the default LocalQueue in `tenant-*` namespaces) gets its batch Job created suspended with the Kueue queue and priority labels, Kueue's Workload state is mapped to phase `Queued` (an eviction requeues, it does not mark the job `Preempted`), and `spec.priority` buckets become `WorkloadPriorityClass`es. With `quotaOperator.kueueIntegration` the quota operator creates a per-tenant LocalQueue, ClusterQueue (cohort `gryvia`, nominal quota from `concurrentGPUs`) and ResourceFlavors, cleaned up by a finalizer. The chart has an optional `kueue` sub-chart (0.19.6, `oci://registry.k8s.io/kueue/charts`), the flags and conditional RBAC; the default render is unchanged. Unit-tested with fake clients and a chart render test; the kind workflow `.github/workflows/e2e-kueue.yml` is written but has not been run, nothing has run on GPUs, and Kueue's runtime behaviour is unverified. See [docs/kueue-integration.md](docs/kueue-integration.md).
- GPU-as-a-service completion (all opt-in except the budget controller; unit-tested, the kind workflow `.github/workflows/e2e-gpuaas.yml` is authored and had not been run, nothing has run on GPUs or against a real identity provider; see [docs/gpuaas-completion.md](docs/gpuaas-completion.md)). Budgets are now computed from `GryviaUsageRecord` spend (`pkg/spend`, `pkg/budget`), with a state machine on `GryviaBudget`, and distributed jobs count `nodes x gpusPerNode` GPUs; the `GryviaBudget` controller is registered. An admission gate (`aiOperator.admissionGate`, `--admission-gate`) rejects a job before its workload is created when a quota or hard budget would be exceeded by metered spend plus a forecast (estimates, fails open on lookup errors). `GryviaReservation` really reserves nodes (`quotaOperator.reservations`, `--enable-reservations`: `gryvia.io/reserved:NoSchedule` taint and labels, recurring schedules; jobs annotated `gryvia.io/reservation` get the toleration). `GryviaTenant` creates per-role RoleBindings to chart-shipped ClusterRoles (`quotaOperator.tenantRbac`, `spec.oidcGroups`). The gateway gets reservation and budget routes and a signed invoice webhook (`GRYVIA_INVOICE_WEBHOOK_URL`); the dashboard and CLI get matching pages and commands. No payments.
- ML controllers: the ai-operator now registers controllers for `GryviaWorkspace` (Pod, Service, optional PVC), `GryviaInferenceService` (Deployment, Service, CPU-based HPA, pod-count canary with auto-promote and auto-rollback), `GryviaModelRegistry` (`autoServe` at stage `production` creates a `GryviaInferenceService`), `GryviaWorkflow` (validated DAG of job, script and webhook steps with retries and timeouts; webhook steps off unless `--workflow-allow-webhooks`) and `GryviaAutoTuner` (trials as child `GryviaAIJob`s, caps `--tuner-max-trials`/`--tuner-max-parallelism`, early stopping and ASHA). They are on by default (`--enable-ml-controllers=false` turns them off); default images and limits are flags, passed through the new `aiOperator.extraArgs`; the chart adds the RBAC; the gateway gets `POST /api/models`. Unit-tested with fake clients; the kind workflow `.github/workflows/e2e-ml.yml` (tiny CPU images) is authored and had not been run; nothing has run on GPUs, with real Jupyter/vLLM/Triton images or with an HPA on real metrics. See [docs/ml-controllers.md](docs/ml-controllers.md).
- Network-intelligence operator wired to real sources (`operators/network-intelligence/pkg/sources`): a collector client (pod discovery by label, HMAC-signed requests with a token read per request, TLS/mTLS, bounded fan-out, merged answers) and a Netra client replace the hard-coded collector URL; `ServiceGraph`, `NetworkAnomaly`, `TrafficInsight` and `SecurityPolicy` read the collector graph, anomalies and alerts, `NetworkCost` reads `GryviaNetworkUsageRecord` and `GryviaNetworkRate`, `TrainingInsight`/`InferenceInsight` read `GryviaFabricSignal` status, `TraceSession` and matched flows read Netra, and `AutoPolicy` writes suggested `GryviaFlowPolicy` objects that it never applies. Every status carries a `SourceAvailable` condition; `spec.autoBlock` is deprecated and ignored. The chart's `operator.sources.*` adds the flags, Secret mounts and RBAC (off by default, default render unchanged). The CLI gets a gateway client (`GRYVIA_GATEWAY_URL`/`--gateway`, `GRYVIA_API_KEY`, `--insecure`, `GRYVIA_CA_FILE`) for network flows and graph, GPU memory and security alerts, and `gryvia gpu rdma` reads `GryviaFabricSignal`. Example scripts and READMEs were fixed and `scripts/check-example-refs.py` checks them. Unit-tested against `httptest` servers and fake clients; `.github/workflows/e2e-netintel.yml` uses a fake collector and had not been run; nothing has run against the real collector fleet, Netra or Cilium. See [docs/network-intelligence-sources.md](docs/network-intelligence-sources.md).
- Observability (opt-in; see [docs/observability.md](docs/observability.md)): the gateway serves Prometheus `/metrics` only when given a token of at least 32 characters (`apiGateway.metrics.*`, never unauthenticated), the quota operator exports quota, usage and tenant gauges, dashboards are generated from `scripts/gen-dashboards.py` and alerts and runbooks (`docs/runbooks/`) reference only metrics some exporter in the repository defines. `monitoring.enabled` renders a PodMonitor, a ServiceMonitor, a PrometheusRule and a Grafana dashboards ConfigMap from `helm/gryvia/monitoring-assets` (skipped without the Prometheus Operator CRDs). The dashboards and rules were never rendered against a live Prometheus or Grafana, alert thresholds are untuned starting points, and no GPU, RDMA NIC or cluster was involved.

- The model factory example served vLLM with `--port=8080` while the operator served and probed the vLLM default 8000, so the pods would never have become ready. `servingConfig.servicePort` is new and passed through to the inference service; the example sets it.
- Docs still called the AIJob lifecycle, Kueue, GPUaaS and ML-controller kind e2e "authored, not yet run" in places (roadmap, ML workflows, scheduling, advanced features, priority, ML controllers, README); all of them, plus MultiKueue and the network-intelligence e2e, passed on `main` on 2026-10-01.
- Docs said the fabric penalty is "a helper that nothing calls"; the job controller has called it behind `--fabric-aware-scheduling` since it was added. README, the Network Intelligence guide and the roadmap now describe it as opt-in and wired.
- Docs still called the Kueue, GPUaaS and ML-controller kind e2e "written but not run"; they pass in CI (with CPU pods; nothing on GPUs). README, FAQ, roadmap, advanced features, scheduling, Kueue and GPUaaS docs corrected.
- eBPF ring signals 11-22 were read and dropped, and the synthesised NIC counter types shared the numbers 11-14 with real ring signals, so a `p2p_fallback` copy size would have been folded into the NIC error rate. NIC types now start at 128; the ten opt-in signals are counted per job (`gryvia_fabric_signal_events{signal}`, `gryvia_fabric_infer_ttft_p99_seconds`), and `weight_mmap` / `gpu_dev` log a warning. Informational only: not in the score and not published to `GryviaFabricSignal` status.
- `GryviaGPUSharingPolicy` did nothing: its reconciler existed but was never registered in the GPU operator, so the NVIDIA one-click time-slicing and MIG labels were never written (the earlier NVIDIA one-click entry said otherwise). It is now registered behind `--enable-gpu-sharing` (chart `gpuOperator.gpuSharing`, off by default because it writes node labels) and has unit tests that check the labels on the nodes. The platform-completion change that removed this controller as a dormant legacy one now keeps it.
- `scripts/deploy-remote.sh` no longer fails with `GRYVIA_NETRA_URL: unbound variable` when the Netra flags are unset, and no longer exits silently after "Installing CRDs ..." (its CRD version check matched only one of the two YAML layouts in `crds/`).
- The release rehearsal showed the eBPF collector image has never built (its kernel programs do not compile). It is no longer published and is off by default in the network-intelligence chart; documented as experimental. (The image builds again since the CO-RE port listed under Added, but it is still not published.)
- Costs are labelled as spend to date; empty states name the operator or collector that feeds the data instead
  of showing reassuring zeros.
- Rate limits count per client address instead of per proxy pod.

### Security
- Seven code-scanning alerts closed: the gateway's session signing key is derived with PBKDF2-HMAC-SHA256 (200,000 iterations, cached) instead of a bare SHA-256, so sessions issued before the upgrade stop validating once; the GPU-count node label is parsed with a 32-bit `ParseInt`; the test TLS server requires TLS 1.2 or newer; `ebpf.yml` and `k3s-bootstrap.yml` run with read-only `contents` permission.
- A finished `GryviaUsageRecord` can no longer be edited through the API (see Added); deleting and recreating one is not blocked.
- Dashboard sessions are signed, expiring tokens issued by `/api/auth/login`; the API key is no longer stored in the browser.
- The dashboard bundle no longer contains a login credential; the gateway validates sign-in.
- The chart runs no root containers: the TLS Secret is mounted with `fsGroup` instead of a root init container.
- Login attempts are constant-time compared, delayed on failure and rate limited per client address.
