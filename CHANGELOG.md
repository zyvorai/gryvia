# Changelog

All notable changes to Gryvia are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the project aims to follow [Semantic Versioning](https://semver.org/) once it leaves alpha.

## [Unreleased]

Entries are newest first within each section. Counts in an entry (for example "24 programs") are as of that entry; the
current numbers are 52 CRDs (32 with a registered controller) and 47 eBPF programs.

### Added
- Placement holds (opt-in: `--placement-holds`, chart `aiOperator.placementHolds`, off by default): while a job's pods come up, the GPUs of the nodes the operator placed it on count as used for other jobs' placement, until all its replicas are ready, it ends or is deleted, or five minutes pass. Before, GPUs counted as used only once a pod was bound to a node, so two jobs placed within seconds of each other were told the same GPUs were free. A single distributed job was already placed all-or-nothing (too few nodes keeps it `Pending`). The hold is in memory and advisory: pods carry a label node selector, not the chosen node names, so with spare matching nodes they can land elsewhere; fabric-aware ranking is unchanged. Unit-tested with fake clients; not run on GPUs. It is not the in-tree gang scheduler, which is still not called.
- Opt-in eBPF programs (`-enable-programs`, chart `ebpf.enablePrograms`): `nccl_transport`, `p2p_fallback`, `capture_gate`, `gpu_oom`, `graph_stall`, `gdr_fail`, `infer_ttft`, `weight_mmap`, `gpu_dev` and `ucx_complete`, whose signals or counters nothing in the collector reads yet, are no longer loaded by default (the collector's loader used to attach every object it found, so `capture_gate` cost a map lookup per TCP send for nothing). The value is a list of names or `all`; an unknown name stops the collector at start. Skipped programs are listed in `/api/v1/ebpf/status` with `notRequested: true` and get no `gryvia_ebpf_program_attached` series.
- eBPF XDP chaining (opt-in: collector flag `-xdp-mux`, chart `ebpf.xdpMux`, needs `-iface`): `xdp_mux` is the interface's only XDP program and tail-calls the first populated slot of `xdp_features`; `roce_cnp`, `pfc_pause`, `dns_tracker`, `packet_filter` and the new `roce_ecn` each tail-call the next populated slot (`ebpf/headers/xdp_chain.h`), so every loaded feature sees every packet instead of one XDP program per interface. The collector's `Manager` attaches the mux and places the features in their slot with a shared prog array (`collector/pkg/loader/xdpmux.go`). Tested in CI with `BPF_PROG_TEST_RUN` and through the collector on the loopback interface; not run on a NIC, and the per-packet cost is unmeasured. A feature attached on its own behaves as before.
- Twelve more observe-only eBPF programs (47 in total): `xdp_mux`, `roce_ecn`, `nccl_transport`, `p2p_fallback`, `capture_gate`, `gpu_oom`, `graph_stall`, `gdr_fail`, `infer_ttft`, `weight_mmap`, `gpu_dev` and `ucx_complete`, with fabric signal types 11 to 22 (14 and 23 are reserved). They build for x86_64 and arm64 and load through the kernel verifier in CI; they have not run on hardware. Nothing in the collector interprets the new signal types yet (the fabric folder ignores them) and the maps that steer `nccl_transport`, `capture_gate` and `gpu_dev` are never written, so ten of them are opt-in (see below). `fabric.TransportHint` classifies `NCCL_*` environment variables but is not called yet.
- Inference canary SLO gating (opt-in): with `aiOperator.inferencePrometheusURL` (flag `--inference-prometheus-url`) the operator reads the canary's 60-second error ratio, p95 latency and request volume from Prometheus with fixed queries, counts measured breaches through the existing health-check rollback policy and blocks promotion on missing, stale or insufficient telemetry (condition `CanaryAnalysisReady`). Default services are unchanged. Not run against a live Prometheus or real traffic; see [docs/inference-serving.md](docs/inference-serving.md).
- Inference GPU/RPS autoscaling and weighted canaries: `targetGPUUtilization` and `targetRequestsPerSecond` now produce HPA Pods metrics (CPU 80% stays the fallback, with a 300 s scale-down window) and an `AutoscalingReady` condition; opt-in Gateway API routing (`aiOperator.inferenceGatewayRouting`) reconciles an owned `HTTPRoute` with stable and canary weights and gates promotion on `Accepted`/`ResolvedRefs`. Needs a custom-metrics adapter and a Gateway controller; tested against a real API server (envtest), not against a data plane, GPUs or live traffic.
- Strict Kueue admission and recovery hooks (opt-in): `aiOperator.kueueStrictAdmission` makes tenant batch jobs fail closed when their LocalQueue is missing and lets queued GPU jobs create their suspended Job without free GPU nodes; optional required worker anti-affinity across hostnames; a cooperative checkpoint `preStop` hook, persistent `/data` and a resume environment contract, with a runnable CPU example. Not run on real GPUs; the hooks do not guarantee a save before eviction. See [docs/admission-recovery.md](docs/admission-recovery.md).
- NVIDIA one-click extras (all opt-in): the NVIDIA Network Operator (`nvidiaNetwork`, with an optional `NicClusterPolicy`) and NIM Operator (`nvidiaNim`) sub-charts, a time-slicing ConfigMap and post-install `nvidia-smi` Job (`nvidiaPlatform`), and `GryviaGPUSharingPolicy` writes the node labels the GPU Operator reads (`nvidia.com/device-plugin.config`, `nvidia.com/mig.config`) once its controller is enabled with `gpuOperator.gpuSharing` (see Fixed: it was never registered before). RDMA, GDS and MIG flags are passed through to the GPU Operator. Chart pins resolve on NGC and image tags were checked; not run on real GPUs, NVSwitch or InfiniBand. See [NVIDIA one-click](website/docs/guides/NVIDIA_ONE_CLICK.md).
- GPU smoke job and evidence collector: `examples/validation/gpu-smoke.yaml` requests one `nvidia.com/gpu` and logs `nvidia-smi`; `scripts/record-gpu-validation.sh` writes the nodes, allocatable GPUs, `GryviaGpuNode` objects and the job log to one report. Not a benchmark; not run on a GPU. See [docs/gpu-validation.md](docs/gpu-validation.md).
- `GryviaUsageRecord` immutability: a validating webhook on `gryviausagerecords` (`quotaOperator.usageRecordWebhook.enabled`, default on, failure policy `Fail`, own certificate and Service) rejects any change to `spec` once `spec.final` is true, including clearing `final`; growth while open, labels, annotations, creates and deletes are allowed. Verified on a live k3s cluster. See [SECURITY.md](SECURITY.md).
- AIJob lifecycle: `training`, `fine-tuning` and `evaluation` `GryviaAIJob`s now run as an Indexed `batch/v1` Job (`inference` stays a StatefulSet; `spec.workloadKind` is the escape hatch, `spec.suspend`, `retryLimit` and `timeout` are honoured, `RANK`/`NODE_RANK` and a namespace-qualified `MASTER_ADDR` are set), so `Succeeded` and `Failed` are reachable and usage records finalize. `Queued`, `Rejected`, `Preempted` and `Cancelled` are honoured by the controller (`Rejected` is sticky), the quota operator patches only `phase`/`message`/`conditions`, and `gpus: 0` runs a CPU-only job. The chart gains RBAC on `batch/jobs`. Never migrated in place: an existing StatefulSet or Job of a job is kept. Unit-tested with fake clients; the kind workflow `.github/workflows/e2e-jobs.yml` is authored and had not been run when this was written; nothing has run on GPUs or RDMA hardware. See [docs/aijob-lifecycle.md](docs/aijob-lifecycle.md), which also lists the order of the gates in `reconcileAIJob`.
- Kueue integration (opt-in, default off; stacked on the AIJob lifecycle): with `aiOperator.kueueIntegration` a job with a queue (`spec.queueName`, annotation `gryvia.io/queue-name`, or the default LocalQueue in `tenant-*` namespaces) gets its batch Job created suspended with the Kueue queue and priority labels, Kueue's Workload state is mapped to phase `Queued` (an eviction requeues, it does not mark the job `Preempted`), and `spec.priority` buckets become `WorkloadPriorityClass`es. With `quotaOperator.kueueIntegration` the quota operator creates a per-tenant LocalQueue, ClusterQueue (cohort `gryvia`, nominal quota from `concurrentGPUs`) and ResourceFlavors, cleaned up by a finalizer. The chart has an optional `kueue` sub-chart (0.19.6, `oci://registry.k8s.io/kueue/charts`), the flags and conditional RBAC; the default render is unchanged. Unit-tested with fake clients and a chart render test; the kind workflow `.github/workflows/e2e-kueue.yml` is written but has not been run, nothing has run on GPUs, and Kueue's runtime behaviour is unverified. See [docs/kueue-integration.md](docs/kueue-integration.md).
- GPU-as-a-service completion (all opt-in except the budget controller; unit-tested, the kind workflow `.github/workflows/e2e-gpuaas.yml` is authored and had not been run, nothing has run on GPUs or against a real identity provider; see [docs/gpuaas-completion.md](docs/gpuaas-completion.md)). Budgets are now computed from `GryviaUsageRecord` spend (`pkg/spend`, `pkg/budget`), with a state machine on `GryviaBudget`, and distributed jobs count `nodes x gpusPerNode` GPUs; the `GryviaBudget` controller is registered. An admission gate (`aiOperator.admissionGate`, `--admission-gate`) rejects a job before its workload is created when a quota or hard budget would be exceeded by metered spend plus a forecast (estimates, fails open on lookup errors). `GryviaReservation` really reserves nodes (`quotaOperator.reservations`, `--enable-reservations`: `gryvia.io/reserved:NoSchedule` taint and labels, recurring schedules; jobs annotated `gryvia.io/reservation` get the toleration). `GryviaTenant` creates per-role RoleBindings to chart-shipped ClusterRoles (`quotaOperator.tenantRbac`, `spec.oidcGroups`). The gateway gets reservation and budget routes and a signed invoice webhook (`GRYVIA_INVOICE_WEBHOOK_URL`); the dashboard and CLI get matching pages and commands. No payments.
- ML controllers: the ai-operator now registers controllers for `GryviaWorkspace` (Pod, Service, optional PVC), `GryviaInferenceService` (Deployment, Service, CPU-based HPA, pod-count canary with auto-promote and auto-rollback), `GryviaModelRegistry` (`autoServe` at stage `production` creates a `GryviaInferenceService`), `GryviaWorkflow` (validated DAG of job, script and webhook steps with retries and timeouts; webhook steps off unless `--workflow-allow-webhooks`) and `GryviaAutoTuner` (trials as child `GryviaAIJob`s, caps `--tuner-max-trials`/`--tuner-max-parallelism`, early stopping and ASHA). They are on by default (`--enable-ml-controllers=false` turns them off); default images and limits are flags, passed through the new `aiOperator.extraArgs`; the chart adds the RBAC; the gateway gets `POST /api/models`. Unit-tested with fake clients; the kind workflow `.github/workflows/e2e-ml.yml` (tiny CPU images) is authored and had not been run; nothing has run on GPUs, with real Jupyter/vLLM/Triton images or with an HPA on real metrics. See [docs/ml-controllers.md](docs/ml-controllers.md).
- Network-intelligence operator wired to real sources (`operators/network-intelligence/pkg/sources`): a collector client (pod discovery by label, HMAC-signed requests with a token read per request, TLS/mTLS, bounded fan-out, merged answers) and a Netra client replace the hard-coded collector URL; `ServiceGraph`, `NetworkAnomaly`, `TrafficInsight` and `SecurityPolicy` read the collector graph, anomalies and alerts, `NetworkCost` reads `GryviaNetworkUsageRecord` and `GryviaNetworkRate`, `TrainingInsight`/`InferenceInsight` read `GryviaFabricSignal` status, `TraceSession` and matched flows read Netra, and `AutoPolicy` writes suggested `GryviaFlowPolicy` objects that it never applies. Every status carries a `SourceAvailable` condition; `spec.autoBlock` is deprecated and ignored. The chart's `operator.sources.*` adds the flags, Secret mounts and RBAC (off by default, default render unchanged). The CLI gets a gateway client (`GRYVIA_GATEWAY_URL`/`--gateway`, `GRYVIA_API_KEY`, `--insecure`, `GRYVIA_CA_FILE`) for network flows and graph, GPU memory and security alerts, and `gryvia gpu rdma` reads `GryviaFabricSignal`. Example scripts and READMEs were fixed and `scripts/check-example-refs.py` checks them. Unit-tested against `httptest` servers and fake clients; `.github/workflows/e2e-netintel.yml` uses a fake collector and had not been run; nothing has run against the real collector fleet, Netra or Cilium. See [docs/network-intelligence-sources.md](docs/network-intelligence-sources.md).
- Observability (opt-in; see [docs/observability.md](docs/observability.md)): the gateway serves Prometheus `/metrics` only when given a token of at least 32 characters (`apiGateway.metrics.*`, never unauthenticated), the quota operator exports quota, usage and tenant gauges, dashboards are generated from `scripts/gen-dashboards.py` and alerts and runbooks (`docs/runbooks/`) reference only metrics some exporter in the repository defines. `monitoring.enabled` renders a PodMonitor, a ServiceMonitor, a PrometheusRule and a Grafana dashboards ConfigMap from `helm/gryvia/monitoring-assets` (skipped without the Prometheus Operator CRDs). CI guards: `scripts/check-metrics-refs.py`, `scripts/check-monitoring-assets.py`, `scripts/sync-monitoring-assets.sh --check`, `promtool check rules`. The dashboards and rules were never rendered against a live Prometheus or Grafana, alert thresholds are untuned starting points, and no GPU, RDMA NIC or cluster was involved.
- Release and verification tooling: `scripts/bench-ebpf-overhead.sh` (loopback benchmark: baseline, noise floor, default and full program sets; one measured run on a single shared x86 host is in [docs/ebpf-overhead.md](docs/ebpf-overhead.md): syscall-heavy code pays the most, and it says nothing about GPU workloads), `scripts/validate-gpu.sh` (automates [docs/gpu-validation.md](docs/gpu-validation.md), JSON report, tested with a fake kubectl; not run on a GPU node), `scripts/upgrade-test.sh` and `scripts/backup-crs.sh` with `.github/workflows/upgrade.yml` (upgrade, rollback and backup/restore round trip on kind; authored, not yet run) replacing the stale `tools/upgrade.sh` and `tools/backup-restore.sh`, `scripts/release-check.sh`, the eBPF collector image in `release.yml` (it has not yet been built by a release) and a `gryvia-crds.yaml` release asset.
- Fabric per-node status and IPv6 network cost (both opt-in; see [docs/fabric-status.md](docs/fabric-status.md) and [docs/network-cost-attribution.md](docs/network-cost-attribution.md)): the collector's `GryviaFabricSignal` patch sends only measured fields and, with `-fabric-status-per-node` (chart `ebpf.fabricStatusPerNode`), server-side-applies its own `status.nodes[]` entry; the ai-operator's `--merge-fabric-signals` (chart `aiOperator.mergeFabricSignals`) folds those entries into the top-level status. `cost_tracker` counts IPv6 in `traffic_costs6`, `netcost` reads it (dual-stack pod cache). Verified with unit tests, `BPF_PROG_TEST_RUN` on Linux 7.0 x86_64 and a faked Kubernetes side; not run end to end on a real cluster, GPU or RDMA hardware.
- Accurate collective identity, NIC counters and GPU correlation for NCCL/RDMA diagnosis (all opt-in except the straggler rewrite, unverified on real GPU/NCCL/RDMA hardware; see [docs/nccl-rdma-gpu-correlation.md](docs/nccl-rdma-gpu-correlation.md)). `straggler.o` now emits one `FABRIC_SIG_COLLECTIVE` per completed collective (rank, world, communicator ordinal, per-communicator sequence, op, bytes, host-side call duration) with identity learned only from public NCCL API uprobes (no NCCL struct offsets), replacing the payload-size heuristic; the Folder matches by (ordinal, sequence, op), the Flight report gains `collectives` and the gateway a cross-node `collectiveComparison`. `-nic-counters` reads `/sys/class/infiniband` hardware counters as rates (retry, error, CNP, pause) because NCCL's userspace verbs path is invisible to the kernel RDMA kprobes; `-ibverbs-probes` attaches `ibv_verbs` (QP and registered-memory counters); `-dcgm-correlate` correlates dcgm-exporter samples with NCCL call windows (`gpuIdleDuringCommRatio`, `smActiveDuringCompute`, `gpuCorrelationCoverage`; informational, not part of `scoreDelta`). CUPTI tracing is not implemented.
- Opt-in tenant network cost attribution (default off; estimates only, no payments; see [docs/network-cost-attribution.md](docs/network-cost-attribution.md)). `-attribute-network` reads the `traffic_costs` map of `cost_tracker` and attributes egress by pod IP to tenants, peer classes (`same-tenant`, `other-tenant`, `cluster`, `external`, `unknown`) and zone classes; `-publish-network-usage` writes hourly `GryviaNetworkUsageRecord` objects into `tenant-<name>` namespaces. New CRDs `GryviaNetworkUsageRecord` and `GryviaNetworkRate` (per-GB rates); gateway `GET /api/network/usage` and `GET /api/network/reconcile` (collector egress against Netra, tolerance 10%); invoices gain `networkLines` and `networkSubtotal` only when records and a rate exist; `gryvia usage --network`; a dashboard table on the Invoices page. Attribution fails closed (ambiguous IPs, hostNetwork pods and stale caches are unattributed) and the collector and Netra figures are never summed.
- Real inference latency and request tracing (opt-in; see [docs/inference-latency.md](docs/inference-latency.md)). The collector scrapes vLLM, Triton and TGI Prometheus endpoints (`-infer-metrics`, `-infer-metrics-discover`) and reports time to first token, inter-token latency, engine queue time, end-to-end latency, waiting requests and KV cache usage as windowed quantiles (`gryvia_inference_*`, and on the `GryviaFabricSignal` status); a figure the engine does not export is absent, never zero, and `inferWaitP99ms` is relabelled as network accept wait, not queue time. `-trace-correlate` consumes `trace_correlator`'s ring, attaches W3C trace ids to Flight Recorder events and serves an HMAC-protected `GET /api/v1/flight/trace`; the gateway route `/api/flight/trace/{id}` is tenant-scoped, `/api/flight/inference/{job}` serves the engine figures, with a job-page panel and `gryvia-flight -inference`.
- Flight diagnosis, persistent incident history and measurement completeness (see [docs/flight-diagnosis.md](docs/flight-diagnosis.md)). `GET /api/v1/flight/diagnosis` (HMAC) ranks evidence-backed findings from Flight events, fabric status and read-only cgroup v2 counters and pressure (CPU throttling, memory, IO) and lists telemetry that was unavailable instead of calling it healthy; the gateway merges nodes (`/api/flight/jobs/{job}/diagnosis`), with `gryvia-flight -diagnosis` and a dashboard card. An optional crash-safe incident store (`-flight-store-dir`) keeps incidents with retention, comparison and export. Measurement completeness counts eBPF ring and perf drops (a `drops` map in the ring-buffer programs), userspace decoder losses, skipped probes and expected-versus-reporting nodes; a node-local report is never complete and the gateway says `unknown` when it cannot tell.
- Flight Recorder command line and dashboard panel: `gryvia-flight` (`collector/cmd/gryvia-flight`, not in the collector image) fetches `GET /api/flight/jobs/{job}` from the gateway with a token read from a file, stdin or `GRYVIA_API_TOKEN` (`-o json|text`, exit 3 with `-require-complete` on a partial or truncated view), and the job detail page has a Flight Recorder card that loads on request. Both mark partial coverage as partial and explain 403 and 503. Unit-tested (Go and vitest) against mocked responses only; not run against a real gateway or cluster.
- Fabric status and quota pacing wiring, all **off by default**. (1) `-publish-fabric-status` (chart `ebpf.publishFabricStatus`): every 30 s the collector patches the `status` subresource of an existing `GryviaFabricSignal` whose `spec.jobRef` matches an attributed job (`overlapIdleRatio`, `cnpRate`, `inferWaitP99ms`, `pfcRate`, `exfilEvents` included; an unmeasured `gdsHitRatio` is cleared, `_unattributed` and `_node/*` are never published, nothing is created) through a small in-cluster REST client (`collector/pkg/kube`, no client-go; `flight` now uses it too), with merge-patch, a 256-job cap and logged, non-fatal errors; with several nodes per job the last writer wins. (2) Fabric signals are now attributed to `(namespace, job)` through the Flight Recorder's PID -> pod -> job resolver (`fabric.Binder`, 5 s cache, at most 4096 pids, fails closed to `_unattributed`). (3) **Mutating:** `GryviaQuota` gets an optional `spec.network.maxEgressMbps` (1 to 32000) and the collector flag `-quota-pace-sync` (needs `-quota-pace` and `-cgroup-path`; chart `ebpf.quotaPace.sync`) reconciles it every 30 s: pods on the node in the quota's namespaces get a 2-minute `Pacer` lease on their pod and container cgroup ids (found under `-cgroup-path` for both kubelet cgroup drivers, symlinks and anything outside the root refused). An API error grants and revokes nothing (leases expire on their own, fail open); `kube-system`, `gryvia-system`, `kube-public`, `kube-node-lease` and the collector's namespace are never paced; `-quota-pace-dry-run` only logs. The cap is per connection and TCP only. The chart adds collector RBAC (`list` on `gryviafabricsignals`, `patch` on `gryviafabricsignals/status`, `list` on `gryviaquotas`) only when the matching value is on; the default render is unchanged. The ai-operator scheduler gains `RescoreNodes` (applies a per-node `scoreDelta` map; inert, nothing calls it and nothing produces such a map). Unit-tested with fakes, and the quota reconcile was run against the real `pace_rate` map and real sockops on a throwaway cgroup tree on Linux 7.0 (Kubernetes calls faked); not tested: a real API server, real quotas on real workloads, GPU or RDMA hardware. See `docs/fabric-status.md`.
- Flight Recorder cluster view: `GET /api/flight/jobs/{job}?namespace=` on the gateway signs a request to every Running collector pod in `apiGateway.flightCollectorNamespace` (HMAC-SHA256 over method, request URI and timestamp with a shared token, 30 s window, replay inside it possible) and merges the node-local reports with a `coverage` field (`total`, `reachable`, `reporting`, `complete`) and a `truncated` flag; tenant callers are limited to their tenant namespaces. The collector's `GET /api/v1/flight/diagnose` now requires that token (`-flight-token-file`, chart values `ebpf.flightTokenSecret` and `apiGateway.flightTokenSecret`) and answers 503 when it is unset; the rest of the collector listener stays unauthenticated. NCCL events carry their operation name and the gateway flags ranks whose observed API duration is an outlier (an API timing, not a GPU or network cause). A Go test and a Python test pin the same signature vector. Unit-tested only; not run against a real cluster.
- Fabric signals, third part: `ucx_gloo` (UCX `ucp_tag_send_nb`/`nbx` calls that blocked >= 5 ms; Gloo is not probed because its C++ symbols are mangled and usually statically linked, so a fixed-symbol probe could never attach; new `-ucx-lib` flag), `pfc_pause` (XDP counter of 802.1Qbb PFC pause frames with per-priority counts, always `XDP_PASS`; only one XDP program can own an interface, so it conflicts with `roce_cnp`, `packet_filter` and `dns_tracker` and the collector now skips a second XDP program with an explicit reason), `weight_exfil` (observe only: a >= 8 MiB read of a model-weight file followed within 30 s by a connect to a non-internal IPv4 address from the same process) and `quota_pace`. **`quota_pace` is the only program that changes sockets** (it lowers `SO_MAX_PACING_RATE` of outbound connections of cgroups that have an entry in its map, never below 1 Mbit/s, fail open): it is **off by default** (new `-quota-pace` flag, which also needs `-cgroup-path`), lease-gated (`fabric.Pacer`, 15 minute lease, expired and shutdown entries are deleted), and **no controller drives it yet** (no `GryviaQuota` watch, no API), so enabling it paces nothing until an operator or future controller writes an entry. The fabric folder adds `pfcRate` (adds 0.10 to `scoreDelta` above 1000 frames per second), `exfilEvents` and `ucxSlowP99ms` (both informational and never part of the score); `pfcRate` and `exfilEvents` are also in the `GryviaFabricSignal` status, and there are `gryvia_pfc_*` and `gryvia_fabric_*` metrics. Verified on Linux 7.0 x86_64 (all 34 objects load; arm64 compiles): `pfc_pause` on crafted frames, `ucx_gloo` on a stand-in library, `weight_exfil` briefly on the live hooks, `quota_pace` on a throwaway cgroup. Unverified: real PFC traffic (many NICs never show pause frames to XDP), real UCX, arm64 hardware and any production use of pacing; an already paced socket keeps its rate until it closes.
- Fabric signals, second part: `overlap` (a `cudaDeviceSynchronize` nested inside an in-flight `ncclAllReduce`), `roce_cnp` (XDP counter of RoCEv2 congestion notifications, always `XDP_PASS`, attached only with `-iface`) and `infer_latency` (accept to first read on inference ports, new `-infer-ports` flag, default `8000,8001`). The fabric folder adds `overlapIdleRatio`, `cnpRate` and `inferWaitP99ms` (also in the `GryviaFabricSignal` status and `gryvia_fabric_*` gauges); the first two add up to 0.15 each to `scoreDelta`, which stays in `[0,1]`. `FabricPenalty` (up to 25 points) is in the ai-operator scheduler package but is not called yet. Load-verified on Linux 7.0 (x86_64, arm64 compiles); `roce_cnp` and `overlap` were also run (test-run packets, stand-in library); real RoCE traffic, GPUs and a live inference server are untested.
- Flight Recorder (node-local preview): the collector keeps a bounded in-memory timeline (2,048 events per job, 128 jobs) of eBPF observations attributed to a `GryviaAIJob` and serves it at `GET /api/v1/flight/diagnose?namespace=&job=`. Identity comes from the host PID's cgroup pod UID matched against the node's pod list (`gryvia.io/job` label) and is never guessed: unresolved or stale (>1 min without a pod-list refresh) PIDs are dropped. `tcp_trace` now emits the retransmission count at connection close (verdict 2) with the PID captured at connect; it is excluded from flow, byte and drop accounting. Fixes: the TrainingInsight controller now reads the collector's real JSON, the NCCL and training analyzers no longer report rank 0 or a topology when the probe has no rank, `GetOpStats` no longer writes under a read lock, NCCL latency samples are bounded, and the Helm collector gets `NODE_NAME`. The endpoint is unauthenticated like the rest of the collector listener (see `docs/flight-recorder.md`); the eBPF change is verified on Linux 7.0 x86_64 only and no cluster-wide aggregation, CLI or GPU/RDMA validation exists.
- Fabric signals: three new eBPF programs (`straggler`, `rdma_health`, `gds_trace`) report NCCL rank skew, RDMA retry/RNR completions and GPUDirect Storage direct-vs-bounce reads on a separate `fabric_signal` ring buffer (`gpu_event` stays 72 bytes; observe-only). The collector decodes them (`collector/pkg/fabric`), folds them per job, and serves them with a `[0,1]` score penalty at `GET /api/v1/fabric` and as `gryvia_fabric_*` gauges; missing optional symbols (`mlx5_ib_*`, `nvidia_fs_read`) are skipped with a log line. New `GryviaFabricSignal` CRD (`gfs`) and `-cufile-lib` flag. Compiled and verifier-checked on Linux 7.0 x86_64 (arm64 compiles only); the GPU, RDMA and GDS paths are unverified on hardware, no controller fills the CRD yet, and the score is not wired into the scheduler.
- The eBPF programs are ported to CO-RE and work: all 24 in `ebpf/` compile (clang 18 and 21, x86_64 and arm64) and pass the kernel verifier on Linux 7.0; no generated `vmlinux.h` (`ebpf/headers/gryvia_core.h`), `make check` loads every object. Many programs had real bugs fixed (wrong syscall-id and register reads, hard-coded struct offsets, connection keys that never matched, unbounded loops, x86-only syscall numbers). The collector image builds again.
- The collector attaches programs by their section name (kprobe, kretprobe, uprobe, tracepoint, raw_tracepoint, tp_btf, XDP, TCX, sockops, sk_msg), tolerates individual failures, dispatches events to the flow, GPU and security decoders, and reports per-program attach results at `/api/v1/ebpf/status`. Verified live on Linux 7.0 (36 of 83 hooks attached, real TCP flows decoded); GPU, RDMA and arm64 paths are not yet verified on hardware.
- Estimate invoices: `/api/invoices`, a dashboard Invoices page and `gryvia invoice` build a monthly per-tenant statement from usage records (JSON or CSV). No payment processing.
- The admission webhook now denies jobs whose GPU type is not allowed by the namespace's quota or the tenant's catalog SKUs, or that exceed the per-job GPU limit; it fails open when the quotas cannot be read.
- GPU as a Service: tenants (`GryviaTenant`, now run by the quota operator) get an isolated `tenant-<name>` namespace; a price catalog (`GryviaGpuSku`); per-job metering (`GryviaUsageRecord`); gateway routes `/api/skus`, `/api/tenants`, `/api/usage` (+ CSV/JSON export); dashboard Catalog, Usage and Tenants pages; and `gryvia catalog`, `gryvia tenant`, `gryvia usage`. See `website/docs/guides/GPU_AS_A_SERVICE.md`.
- Roles in the gateway: the API key and sessions are the provider admin; OIDC users are tenant users limited to their tenant's namespaces (`GRYVIA_OIDC_ADMIN_GROUPS` promotes a group). Cluster-wide routes (nodes, network, security, GPU metrics) are admin-only.
- Network flows can come from [Netra](https://github.com/zyvorai/netra): set `apiGateway.netra.url` and `/api/network/flows` returns Netra's recent flows (falls back to service-graph edges when it is unset or unreachable).
- Workflows and auto tuners can be deleted from the dashboard and the gateway (`DELETE /api/workflows/{name}`, `DELETE /api/tuners/{name}`).
- GPU nodes prepare themselves: the chart can bundle NVIDIA's GPU Operator (`nvidia.enabled=true`: driver, container toolkit, device plugin, DCGM, node feature discovery), and `scripts/install-k3s-gpu.sh` takes a fresh Ubuntu server to k3s + Gryvia + GPU support (`agent` mode joins more nodes). CI runs the script on a real k3s (without a GPU) and dry-run tests for the GPU branches. See `website/docs/guides/GPU_NODES.md` and `docs/gpu-validation.md`.
- The GPU operator registers a `GryviaGpuNode` for every node labelled by NVIDIA GPU feature discovery (`--auto-register`, chart value `gpuOperator.autoRegister`) and reads readiness, driver and CUDA versions from the node's labels and allocatable GPUs; per-GPU numbers come from the DCGM exporter on that node.
- CLI in the style of `cilium`: colored `--help` with commands in groups, examples on every command, aliases, `--no-color`/`NO_COLOR`, shell completions (`gryvia completion`), `gryvia version`, concise errors with hints, and one output look (aligned tables with OK/Warning/Error markers) across all commands.
- `gryvia status` reports the whole platform like `cilium status`: a component banner, workload readiness, cluster totals, image versions, errors and a per-node table (GPU health, driver, DaemonSet pods, maintenance). `--brief`, `--wait`, `--node`, `-o json|yaml`; exits 1 when a required component fails. `-o json|yaml` is also available on `cluster`, `quota`, `queue` and `maintenance list`.
- Helm chart `helm/gryvia` installs the operators, API gateway and dashboard in one release, with optional
  Ingress, cert-manager TLS, PodDisruptionBudgets and a NetworkPolicy.
- Tag-driven release workflow: multi-arch images on ghcr.io (mirrored to Docker Hub), signed with cosign,
  OCI Helm chart and CLI binaries.
- `scripts/install.sh` and `scripts/kind-demo.sh` (a GPU-free demo with fictional data on kind).
- `POST /api/auth/login` on the gateway with rate limiting, a `usingDefaultKey` flag on `/api/auth/me`, and a
  dashboard warning while the default lab key is in use. `auth.apiKey=""` generates a random key.
- Dashboard: job logs, events and pods; searchable, sortable, paginated tables with URL state; create forms for
  traces and security policies; structured editors for tuner parameter spaces and workflow steps.
- Accessibility pass: skip link, focus management, modal focus trapping, table captions, text alternatives for
  the service graph, heat map and charts.
- Open tabs recover automatically after a redeploy.

### Changed
- `GryviaEbpfProgramNotAttached` no longer fires for programs the configuration did not ask for. The collector exported `gryvia_ebpf_program_attached = 0` for every skipped program, so quota pacing, the libibverbs probes, `xdp_mux`, `infer_latency` without `-infer-ports`, XDP/TCX without `-iface` and sockops without `-cgroup-path` all alerted on every node by default. Those are now marked `notRequested: true` in `/api/v1/ebpf/status` and get no series. A missing library or symbol, an interface that already has an XDP program, and a failed attach still export 0 and can alert. The `count(gryvia_ebpf_program_attached == 0)` dashboard panels show fewer zeros accordingly.
- `scripts/deploy-remote.sh` keeps the installed API key on a redeploy: an explicit `GRYVIA_API_KEY`, else the `gryvia-api-key` Secret, else `~/.gryvia/api-key`, and the lab default only on a first install; it prints the key only when it is the default. Before, every deploy reset the key to `GRYVIA_API_KEY` or the lab default.
- `roce_cnp`, `pfc_pause`, `dns_tracker` and `packet_filter` end by chaining to the next XDP slot (`headers/xdp_chain.h`); attached on their own they behave as before.
- Chart cleanup: keys no template read were removed from `helm/gryvia` (`ha.enabled`, `crds.install`, `crds.keep`, `gpuOperator.healthCheck.*`, `quotaOperator.pricing.*`, top-level `labels` and `annotations`) and from `helm/network-intelligence` (`security.enabled`, `security.autoBlock`, `ha.enabled`, `labels`, `annotations`); setting them was already a no-op. `scripts/check-chart-values.py` (run in `repo-checks.yml`) fails when a value is not read by a template. The default `helm/gryvia` render now differs from the previous release only by RBAC: `batch/jobs` for the Job workload and the ML controllers' rules (`apps/deployments`, `horizontalpodautoscalers`, the five ML kinds).
- **Breaking for chart users who relied on it:** `helm/gryvia` `namespace.create` now defaults to `false`. With `true`, the documented `helm install ... --namespace gryvia-system --create-namespace` failed with `namespaces "gryvia-system" already exists` (Helm creates the release namespace before the chart's Namespace object). Set `namespace.create=true` only for flows that do not use `--create-namespace`. `install-k3s-gpu.sh` pre-creates the namespace with the privileged Pod Security label when a GPU is present.
- `helm/network-intelligence`: the operator Deployment no longer passes `--security-enabled`/`--security-auto-block`, which the operator does not define (it exited at start-up); the install notes no longer claim security monitoring or auto-blocking. `security.*` values are reserved.
- Documentation refreshed against the code: the API reference now lists every gateway route with its access rule (there is no `/api/v1` prefix and no webhook, WebSocket or `/metrics` endpoint on the gateway); the CRD reference has a Controller column generated from `operators/*/main.go` and states the real API version; the admin guide, quick start, chart READMEs, SECURITY.md, the ebpf and collector READMEs and the guides were corrected, and design-only material (kinds without a controller, multi-cluster, disaster recovery, budgets, gang scheduling and fair-share queues, which exist only as library code) is labelled as such. `scripts/gen-crd-docs.py` reads the version from the CRDs instead of hard-coding `v1`.
- CI: `ebpf.yml` expects 30 compiled programs on the arm64 cross-build (it still said 24); the legacy-name check in `repo-checks.yml` no longer matches the current `GryviaFabricSignal` kind or the `FabricPenalty` helper. `scripts/check-examples.py` (run in the docs-accuracy job) now also validates the fenced `yaml` manifests in the Markdown docs against the CRD schemas, as its description already claimed.
- Fixed struct-layout mismatches between the eBPF programs and the collector's Go decoders (implicit padding made every field after the gap misread; security and GPU enums disagreed).
- The `network-intelligence` chart now runs the collector with the flags it actually has (`ebpf.interface`, `ebpf.cgroupPath`, `ebpf.ncclLib`, `ebpf.cudaLib`); the old `--enable-program` list is gone.
- **Breaking for OIDC installs:** an OIDC token must now match a `GryviaTenant` (by `org` or `groups`); previously the claim was trusted as a namespace and every user could read cluster-wide data. Set `apiGateway.oidc.legacyNamespaces=true` only while no tenants exist.
- Quota enforcement rejects jobs whose GPU type is not allowed; GPU prices come from the SKU catalog (one shared default table replaces two hardcoded copies).
- The GPU operator no longer uses NVML: it runs without cgo on a distroless static image. It previously read GPU data inside its own pod, so it reported the wrong node and normally could not load the driver. `spec.drivers` is informational; nothing consumes it.
- The bundled NVIDIA device plugin and DCGM exporter DaemonSets only run on nodes labelled `nvidia.com/gpu.present=true` (configurable) and are skipped when the GPU Operator sub-chart is enabled. Previously they ran, and crashed, on every node.
- Docs no longer claim the Terraform/Ansible flow installs Kubernetes, Calico, Multus or GPU drivers; those directories are marked experimental and incomplete.
- **Breaking:** the API version is now `gryvia.io/v1alpha1` (it was `v1`), matching the project's alpha status. Objects created under `v1` are not converted: export them, change `apiVersion`, and re-apply. `scripts/rename-version.sh` documents the change; `deploy-remote.sh` recreates CRDs that still store `v1` when they hold no objects.
- **Breaking:** API kinds renamed from `Fabric*` to `Gryvia*` (for example `FabricAIJob` is now `GryviaAIJob`).
  Recreate existing objects under the new kinds; `scripts/rename-kinds.sh` documents the mapping.
- The dashboard follows netra's design system and defaults to the system light or dark setting.
- Status vocabulary unified across pages (`Succeeded` counts as completed, `Scheduling` as pending).

### Fixed
- eBPF ring signals 11-22 were read and dropped, and the synthesised NIC counter types shared the numbers 11-14 with real ring signals, so a `p2p_fallback` copy size would have been folded into the NIC error rate. NIC types now start at 128; the ten opt-in signals are counted per job (`gryvia_fabric_signal_events{signal}`, `gryvia_fabric_infer_ttft_p99_seconds`), and `weight_mmap` / `gpu_dev` log a warning. Informational only: not in the score and not published to `GryviaFabricSignal` status.
- `GryviaGPUSharingPolicy` did nothing: its reconciler existed but was never registered in the GPU operator, so the NVIDIA one-click time-slicing and MIG labels were never written (the earlier NVIDIA one-click entry said otherwise). It is now registered behind `--enable-gpu-sharing` (chart `gpuOperator.gpuSharing`, off by default because it writes node labels) and has unit tests that check the labels on the nodes. The platform-completion change that removed this controller as a dormant legacy one now keeps it.
- `scripts/deploy-remote.sh` no longer fails with `GRYVIA_NETRA_URL: unbound variable` when the Netra flags are unset, and no longer exits silently after "Installing CRDs ..." (its CRD version check matched only one of the two YAML layouts in `crds/`).
- The release rehearsal showed the eBPF collector image has never built (its kernel programs do not compile). It is no longer published and is off by default in the network-intelligence chart; documented as experimental. (The image builds again since the CO-RE port listed under Added, but it is still not published.)
- Costs are labelled as spend to date; empty states name the operator or collector that feeds the data instead
  of showing reassuring zeros.
- Rate limits count per client address instead of per proxy pod.

### Security
- Seven code-scanning alerts closed: the gateway's session signing key is derived with PBKDF2-HMAC-SHA256 (200,000 iterations, cached) instead of a bare SHA-256, so sessions issued before the upgrade stop validating once; the GPU-count node label is parsed with a 32-bit `ParseInt`; the test TLS server requires TLS 1.2 or newer; `ebpf.yml` and `k3s-bootstrap.yml` run with read-only `contents` permission.
- A finished `GryviaUsageRecord` can no longer be edited through the API (see Added); deleting and recreating one is not blocked.
- Dashboard sessions are signed, expiring tokens issued by `/api/auth/login`; the API key is no longer stored in the browser.
- The dashboard bundle no longer contains a login credential; the gateway validates sign-in.
- The chart runs no root containers: the TLS Secret is mounted with `fsGroup` instead of a root init container.
- Login attempts are constant-time compared, delayed on failure and rate limited per client address.
